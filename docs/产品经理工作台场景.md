# 面向产品经理的 DSH 可交互工作台：可插件化场景设计

> 目标不是“再做一个需求列表页”，而是把 PM 的四类高频工作——**需求分析、原型设计、PRD 撰写、产品测评**——变成可复用、可追溯、能把上下文交给 Agent 的工作流。
>
> 工作台负责「看见、筛选、比较、决策」；Agent 负责「归纳、生成、评审、补全」；数据源负责「事实」。三者边界清晰，页面才不会变成又一个信息孤岛。

---

## 1. 产品主张：Evidence → Decision → Artifact → Handoff

一条完整链路：

```
多来源证据（客服/销售/商店/表单/内部）
        ↓
需求池（可筛选、可比较多维信号）
        ↓
工作包（勾选 + 工作模式 + 上下文预览）
        ↓
Agent 会话（Preset + Playbook + 团队规范）
        ↓
产出物（评审纪要 / PRD / 原型 / 测评方案）
        ↓
写回与追踪（Base 状态、PM 结论、版本）
```

工作台的竞争力不在“展示”，而在四个闭环：

1. **证据闭环**：每条需求能回到原话、来源、提出方、影响人数。
2. **决策闭环**：统一 rubric，而不是谁声音大谁先做。
3. **产出闭环**：从需求直接生成评审纪要/PRD/原型/测评方案。
4. **学习闭环**：上线后的测评结果反哺下一轮需求判断。

## 2. 六个可插件化场景

### 场景 A：多来源需求归并（Demand Clustering）

| 项 | 内容 |
|---|---|
| 触发 | 每周一/每两周，或新版本规划前 |
| 输入 | 飞书需求池；客服工单；销售转述；应用商店评价；C 端表单；内部反馈 |
| 处理 | 主题聚类、重复诉求识别、影响面合并、来源可信度加权 |
| 输出 | 主题簇卡片（条数、平均机会分、覆盖人数、代表原话、涉及模块） |
| DSH 形态 | 工作台「洞察」tab + Agent Preset `research-analyst` + Skill「需求聚类」 |
| 数据源 | Base 为主；评价/工单可作为第二数据源，先做只读聚合 |
| MVP | 页面按标签/模块聚类 + Agent 生成主题簇说明 |
| 关键指标 | 重复需求识别率、PM 归并耗时、遗漏场景数 |

**为什么值得插件化**：聚类规则会随团队变化（按模块/按客户/按场景），适合做成可配置 Playbook + Skill，而不是写死在页面。

---

### 场景 B：需求评审（Demand Review）

| 项 | 内容 |
|---|---|
| 触发 | 需求进入排期前；P0/P1 争议时 |
| 输入 | 选中需求；六维评分（商业价值、战略契合、影响规模、证据置信、紧急度、成本可控）；历史评审案例 |
| 处理 | 计算机会分、生成评审问题、识别缺失证据、给出「进入/补信息/暂缓」建议 |
| 输出 | 评审纪要（可复制到飞书文档）、风险清单、待补证据 |
| DSH 形态 | 工作台「评审」tab + Preset `product-manager` + Skill「六维评审」 |
| 数据源 | Base + PRD/测评案例库 + 开发协作规范（成本/依赖） |
| MVP | 页面内 rubric + 自动纪要；Agent 只做补全和质疑 |
| 关键指标 | 评审准备时间、评审一次通过率、返工率 |

**设计要点**：
- 评分是**决策辅助**，不是自动排期。页面显示“建议优先级”，最终仍由 PM 修改并写回。
- 证据不足的需求（置信度 ≤3）应被显式标出，而不是给一个看似精确的高分。
- 评审纪要要保留「谁提出、原话是什么、影响多少人」，避免会开完只剩结论。

---

### 场景 C：PRD 工坊（PRD Studio）

| 项 | 内容 |
|---|---|
| 触发 | 需求评审通过后 |
| 输入 | 选中需求；团队 PRD 模板；设计组件规范；开发协作规范；历史 PRD |
| 处理 | 生成背景/目标/非目标/用户场景/范围/方案/验收/风险/待确认 |
| 输出 | 可评审的 PRD 初稿（Markdown/飞书文档），带需求 ID 溯源 |
| DSH 形态 | 工作台「PRD 工坊」+ Preset `product-manager` + Skill「PRD 模板」+ 文档写入工具 |
| 数据源 | Base + 设计规范 + 开发规范 + 历史 PRD |
| MVP | 页面本地生成结构化初稿 + 复制/下载 + 交给 Agent 补全 |
| 关键指标 | PRD 初稿耗时、评审打回次数、验收标准完整率 |

**模板结构（Demo 采用）**：

1. 背景与问题（含来源、影响人数、代表原话）
2. 目标与非目标
3. 用户与场景
4. 需求范围（逐条 ID + 优先级 + 模块）
5. 方案要点（交互/数据/协作/模块拆分）
6. 验收标准
7. 风险、依赖与待确认

**插件化建议**：模板不要写死在客户端。可以让 `plugin Config` 指向一个 Base/文档中的模板，或通过 Skill 读取团队最新模板；页面只负责组装上下文。

---

### 场景 D：原型草图（Prototype Guidance）

| 项 | 内容 |
|---|---|
| 触发 | PRD 初稿后、设计评审前 |
| 输入 | 需求；信息架构约束；设计组件规范（token/组件用法）；页面模板 |
| 处理 | 推导 IA、关键流程、页面区块、交互状态、组件映射 |
| 输出 | 低保真线框（ASCII/结构化清单）、组件映射表、必须/可后置标注 |
| DSH 形态 | 工作台「场景库」→ 原型 Playbook + Preset `prototype-designer`；产出可落到画板/HTML 原型 |
| 数据源 | 设计组件规范 + 历史页面模板 + Base 需求 |
| MVP | 页面生成“IA + 区块 + 组件映射”的结构化建议，交给 Agent 画线框 |
| 关键指标 | 原型返工次数、设计评审问题数、组件复用率 |

**为什么不是“一键生成 Figma”**：真正的瓶颈不是画图，而是**信息架构和状态覆盖**。页面先把 IA/状态/组件映射讲清楚，Agent 再画图，返工更少。

---

### 场景 E：产品测评（Product Evaluation）

| 项 | 内容 |
|---|---|
| 触发 | 上线前设计测评方案；上线后复盘 |
| 输入 | PRD/需求；成功指标；历史测评案例；埋点规范 |
| 处理 | 目标与假设、样本、任务脚本、成功指标、对照方案、判定标准、风险 |
| 输出 | 测评方案 + 任务脚本 + 指标口径 + 判定规则 |
| DSH 形态 | 工作台「场景库」→ 测评 Playbook + Preset `qa-reviewer` + Skill「测评方案」 |
| 数据源 | 历史测评案例 + 指标库 + Base 需求 + 线上数据（可选） |
| MVP | 页面生成测评方案骨架；Agent 补全任务脚本和指标 |
| 关键指标 | 测评方案覆盖率、指标口径争议数、上线后验证周期 |

**设计要点**：
- 区分「上线前可用性测评」与「上线后效果评估」，不要把两者混成一个模板。
- 指标必须可计算；页面应要求填基线/目标/数据来源。
- 测评结果要能写回需求记录，形成学习闭环。

---

### 场景 F：竞品拆解（Competitive Teardown）

| 项 | 内容 |
|---|---|
| 触发 | 新方向探索、版本对标、销售竞标支持 |
| 输入 | 应用市场评价；竞品功能清单；需求池中的差异化诉求 |
| 处理 | 能力对比矩阵、评价高频抱怨、差异化机会、不可跟风项 |
| 输出 | 对比矩阵 + 机会点 + 3 条可验证假设 |
| DSH 形态 | 工作台「场景库」→ 竞品 Playbook + Preset `research-analyst` + Web 搜索/评价抓取 |
| 数据源 | 应用商店评价 + 竞品资料 + 内部需求池 |
| MVP | 页面提供对比矩阵模板；Agent 做资料补充与归纳 |
| 关键指标 | 竞品结论被引用次数、差异化需求占比 |

### 备选场景（V2 再考虑）

| 场景 | 价值 | 依赖 |
|---|---|---|

## 3. 插件化架构：一个 Shell + 多个 Playbook + 可替换数据源

```
┌──────────────────────────────────────────────────────────────┐
│ 需求台 Shell（DSH Client 插件页）                            │
│  需求池 · 洞察 · 评审 · PRD · 场景库                          │
│  多选 / 工作包 / 发送到 Agent / 写回                          │
└───────────────┬──────────────────────────────┬───────────────┘
                │                              │
        ┌───────▼────────┐            ┌────────▼─────────┐
        │ Playbook 注册表 │            │ Data Adapter 层   │
        │ analysis        │            │ Feishu Bitable    │
        │ review          │            │ Design tokens     │
        │ prd             │            │ Dev conventions   │
        │ prototype       │            │ PRD/eval cases    │
        │ evaluation      │            │ Skills hub        │
        │ competitive     │            │ Analytics (opt.)  │
        └───────┬────────┘            └────────┬─────────┘
                │                              │
        ┌───────▼──────────────────────────────▼─────────┐
        │ DSH Agent（Preset + Skill + Tools）              │
        │ 产出：分析/评审/PRD/线框/测评/竞品矩阵            │
        └────────────────────────────────────────────────┘
```

### 3.1 Playbook 的插件化接口

一个 Playbook 最少包含：

```ts
interface Playbook {
  id: string
  title: string
  mode: 'analysis' | 'review' | 'prd' | 'prototype' | 'evaluation' | 'competitive'
  agentPreset?: string          // 绑定 Agent 能力
  dataSources: DataSourceId[]   // 需要哪些事实源
  buildPrompt(records, context): string
  output: 'markdown' | 'docx' | 'prd' | 'wireframe' | 'eval-plan'
  reviewRubric?: Rubric
}
```

页面只负责：

- 选择记录；
- 选择 Playbook；
- 预览/编辑 prompt；
- 调用 `startSession({ prompt, agentPreset })`；
- 把结果写回 Base 或文档。

这样新增场景 = 新增 Playbook + 数据源，不需要改页面骨架。

### 3.2 数据源适配器

| 数据源 | 事实内容 | 接入方式 | 读/写 | 备注 |
|---|---|---|---|---|
| 飞书多维表 | 需求池、状态、评分、PM 结论 | `lark-cli base` / Bitable OpenAPI | 读 + 写 | Demo 已接入 |
| 设计组件规范 | token、组件用法、页面模板 | 文档/Base/Figma API | 只读 | 建议先做静态快照 |
| 开发协作规范 | 接口、权限、发布、灰度 | 文档/Wiki | 只读 | 可做成 Skill |
| PRD/测评案例库 | 历史模板、评审案例、指标 | 文档/Base | 只读 | 用于 few-shot/检索 |
| 企业内部 Skills 中台 | 可执行能力 | Skills 注册表 | 只读/调用 | 与 Agent Preset 配合 |
| 线上数据 | 使用量、留存、性能 | 数仓/埋点 | 只读 | V2 |

**原则**：页面不直接持有第三方密钥；所有外部事实通过 Host 路由/工具获取；写操作走白名单。

## 4. 交互设计原则

1. **先选择，再发送**：不要让 Agent 在没有上下文时猜；也不要一键自动发送。工作包弹窗是“确认合同”。
2. **证据优先**：每条判断都要能回到需求 ID/原话；没有证据就标“待验证”。
3. **评分透明**：显示六个维度和权重，允许 PM 覆盖建议；不要把算法结果伪装成客观真理。
4. **写回可控**：只允许写回优先级、状态、PM 结论等少量字段；字段映射集中在 Host。
5. **空状态有用**：没有数据时告诉用户“去同步/去飞书表”，而不是空白。
6. **失败可恢复**：同步失败保留上次快照；写回失败给出具体原因；不要静默吞错。
7. **不重复造宿主能力**：主题、Locale、会话、权限、文件用 DSH 服务；页面只做业务。

## 5. 分阶段路线图

### MVP（本次 Demo）

- 飞书 Base 数据源 + 22 条示例需求
- 需求池筛选/排序/多选
- 洞察：来源、部门、机会矩阵、模块聚类、决策信号
- 评审：六维 rubric + 纪要
- PRD：模板化初稿 + 复制/下载/交给 Agent
- 场景库：6 个 Playbook + 数据源状态
- 写回：优先级/状态/PM 结论
- 发送：新会话 draft（`startSession`）

### V1（可上线给 5–10 位 PM 试用）

- Base 字段映射配置化（`plugin Config`）
- 真实设计规范/开发规范接入（只读快照 + 检索）
- 评审纪要写回飞书文档
- Agent Preset 绑定（product-manager / prototype-designer / qa-reviewer）
- 同步状态与失败重试
- 需求变更历史/审计

### V2（团队级工作台）

- 多 Base / 多团队空间
- 需求去重与主题聚类（向量/规则混合）
- 原型线框生成与设计规范校验
- 测评方案 + 上线后指标回填
- 周报/路线图自动生成
- 权限与字段级脱敏

## 6. 衡量工作台是否真的有用

| 指标 | 定义 | 目标（试用期） |
|---|---|---|
| 需求归并耗时 | 从收集到形成主题簇的时间 | 下降 50% |
| 评审准备时间 | 会前整理材料的时间 | < 15 分钟/批 |
| 证据完整率 | 有原话+来源+影响人数的需求占比 | > 90% |
| PRD 一次通过率 | 评审无需大改的比例 | 提升 20% |
| 需求返工率 | 进入开发后因理解偏差返工的比例 | 下降 30% |
| Agent 工作包使用率 | 使用过工作包/周活 PM | > 60% |
| 写回准确率 | 页面写回 Base 的成功率 | > 99% |

---

## 7. 一句话总结

**把“需求台”做成一个 Shell：页面负责证据与决策，Playbook 负责场景，Preset/Skill 负责 Agent 能力，Data Adapter 负责事实源。** 这样产品经理得到的不是又一个看板，而是一条从“用户原话”到“可评审产出”的可复用生产线。
